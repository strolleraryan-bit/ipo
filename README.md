# Lot & Ledger — IPO Manager PWA

A single-file, offline-first Progressive Web App for tracking IPO applications, funding, GMP, profit/loss, and money owed between you and the people you apply on behalf of. No build step, no backend, no external database — everything lives in the browser's `localStorage`.

## Files

```
pwa/
├── index.html          ← the entire app (HTML + CSS + JS in one file)
├── sw.js                ← service worker (offline caching)
├── manifest.json        ← PWA manifest (name, icons, theme)
└── icons/
    ├── icon-192.png
    ├── icon-512.png
    ├── icon-maskable-192.png
    └── icon-maskable-512.png
```

**The only file you'll typically need to edit is `pwa/index.html`.** It contains all markup, styles, and logic — the app is intentionally kept as one file for easy deployment (drag-and-drop to Netlify, or open directly in a browser).

## How to run it

- **Locally:** open `pwa/index.html` directly in a browser, or serve the `pwa/` folder with any static file server.
- **Deploy:** drag the `pwa` folder onto Netlify (or any static host). No build command, no environment variables.
- **Install as an app:** once deployed over HTTPS, most browsers offer "Add to Home Screen" / "Install" thanks to `manifest.json` and `sw.js`.

## Data storage

- All data (IPOs, applications, users, transfers, withdrawals) is stored in the browser's `localStorage` under the key `lotledger-app-state`.
- Data is **per-browser, per-device** — it does not sync across devices or accounts on its own.
- Use **Export Backup** (Dashboard → Backup section) regularly. This downloads a `.json` file with the complete app state.
- Use **Import Backup** to restore or move data to another browser/device — just open the app fresh and import the `.json` file.

## App structure (inside index.html)

- **State shape:**
  ```js
  state = {
    users: [],          // includes one user with isMe:true (the account owner)
    ipos: [],            // IPO records: name, dates, price, lot size, GMP, listing price, notes
    applications: [],    // one per (user, ipo): lots, profitMode ('commission'|'assisted'|'shared'), fundedByMe
                          // (Aryan's invested amount — his stake, drawn from Account A; for Assisted/Shared this
                          // is only PART of the applied cost, the rest — cost-fundedByMe — is the user's own
                          // stake from Account B, mirrored in `userInvested` for Assisted mode display),
                          // amountGiven (total cash handed over, may exceed fundedByMe), commissionPercent
                          // (Commission and Assisted modes), bonusToUser (Shared mode only — flat extra profit
                          // Aryan gives the user above the ratio split), allotment/sale results. Legacy records
                          // use the old `fundingSource` field ('me'|'shared'|'own') which is auto-migrated on
                          // read via profitModeOf().
    transactions: [],    // money transfers between ANY two tracked users (fromUserId/toUserId/amount) —
                          // fully synchronized: deducted from the sender's balance, added to the receiver's,
                          // computed live from this array so deleting a transfer automatically undoes it on
                          // both sides. Every leg touching a non-Aryan user is also tagged fromAccount and/or
                          // toAccount ('A'|'B') — Aryan→user always tags toAccount:'A'; user→Aryan always
                          // tags fromAccount:'A'; an internal move (see below) has fromUserId===toUserId with
                          // differing fromAccount/toAccount. This is also how Aryan actually "collects" money
                          // from a user's Account A.
    withdrawals: [],     // cash withdrawals per user, reduce that user's tracked balance. Non-Aryan entries
                          // carry `account` ('A'|'B'); legacy entries without it default to 'A'.
    deposits: []          // cash deposits for ANY user now (not just Aryan) — "Add Cash to Account". For
                          // Aryan (isMe) this tops up his single liquid balance; for every other user it
                          // always credits their Account B (their own money).
  }
  ```
- **Core money logic** lives in a handful of functions — read these first before making balance-related changes:
  - `computeApp(app, ipo, user)` — the single source of truth for an application's status (pending/holding/refunded/settled), profit split, and `owedToMe` (everything currently owed to Aryan from this application, whether it's principal awaiting allotment result, blocked capital while holding, or settled-but-not-yet-transferred principal+profit) at every stage.
  - `profitModeOf(app)` — resolves an application's profit-sharing mode, migrating legacy `fundingSource` records.
  - `transfersNet(userId)` — generalized, synchronized ledger helper: sum of every transaction where this user is the receiver (+) minus every one where they're the sender (−). Used identically for Aryan and for every friend, and for x↔y transfers between two friends that don't involve Aryan at all.
  - `transfersNetAccount(userId, account)` — same idea, scoped to one sub-account (`'A'`|`'B'`) of a non-Aryan user: only counts a transaction on the side(s) where its `fromAccount`/`toAccount` tag matches. This is what lets an internal A↔B move (same user on both sides) correctly shift money between the two account totals instead of netting to zero.
  - `appAccountALock(app, ipo, user)` / `appAccountBLock(app, ipo, user)` — how much of a single application is currently "locked" out of a non-Aryan user's Account A / Account B respectively: `extraGiven` is always locked out of A (permanently owed until transferred back); the application's Aryan-funded share is locked out of A only while pending/holding and releases automatically (plus profit) once settled; the user's own share (`fullCost − aryanInvested`) is locked out of B the same way, releasing (plus their commission/profit share) once settled. Refunded applications release both locks with no profit/loss.
  - `accountABalance(userId, excludeAppId?)` / `accountBBalance(userId, excludeAppId?)` — a non-Aryan user's two real wallet balances: `accountA = opening + transfersNetAccount(userId,'A') − withdrawalsFor(userId,'A') − Σ appAccountALock(...)`; `accountB = depositsFor(userId) + transfersNetAccount(userId,'B') − withdrawalsFor(userId,'B') − Σ appAccountBLock(...)`. Pass `excludeAppId` to exclude one application's own current lock — used when re-validating balance while editing a still-pending application, so it doesn't count its own existing commitment against itself.
  - `userBalance(userId)` — a friend's full balance record: `{owed, transfers, withdrawn, opening, accountA, accountB, net}` where `net = accountA + accountB` (positive = total money currently tracked in their two accounts).
  - `myDeployedCapital()` — Aryan's capital currently blocked: for friend applications this stays blocked **indefinitely** (pending → holding → refunded → settled) until a real transfer collects it back; for Aryan's own (isMe) applications it's blocked only while pending/holding, releasing automatically at settlement.
  - `myOwnRealizedProfit()` — profit from Aryan's own (isMe) applications only, credited immediately at settlement (no intermediary user account involved).
  - `myAccountBalance()` — Aryan's **liquid** cash only: `opening + deposited − withdrawn + transfersNet(me) − myDeployedCapital() + myOwnRealizedProfit()`. Deliberately does NOT include a friend's unrealized profit/principal — that only lands here once an actual transfer transaction moves it (see "Transfer to Aryan" below).
  - `totalInOthersAccounts()` — dashboard aggregate: sum of `accountABalance(u.id) + accountBBalance(u.id)` across every non-Aryan user.
  - `myTotals()` — dashboard-wide stats (capital deployed, profit, outstanding, IPO counts).
- **The two-account model (Account A / Account B) — every non-Aryan user has exactly two tracked wallets, both real, checkable balances rather than an open-ended receivable:**
  - **Account A** holds Aryan's own money sitting with that user: every transfer Aryan sends them, plus Aryan's principal/profit from their settled or refunded applications that hasn't been transferred back to Aryan yet. The application's opening balance is also treated as Account A. This is the **only** account an application's Aryan-funded share is ever deducted from, and the **only** account a "Transfer to Aryan" is ever drawn from.
  - **Account B** holds the user's own money: cash they've added themselves via "Add Cash to Account" (deposits, now available to every user, not just Aryan), plus their own commission/profit share from settled applications. This is what their own share of a Shared Investment application is deducted from.
  - **Applying to an IPO actually draws down these balances**, rather than creating debt from nothing: Commission Model draws the full applied cost from Account A only; Shared Investment draws Aryan's entered share from Account A and the remaining share (`cost − Aryan's share`) from Account B. `saveApp()` blocks the save (new applicants always; edits only while the application is still pending) if either required account can't cover its share — this is the fix for applicants being added with no money in their account.
  - Money automatically reappears in the relevant account once an application is refunded (full amount, no profit/loss) or settled (profit/commission credited) — no manual "return" step needed, because the per-application lock simply stops being subtracted.
  - **Move Between Account A ↔ B** (`openMoveModal`/`saveMove`) lets any non-Aryan user move their own tracked money between the two accounts — logged as a `state.transactions` entry with `fromUserId===toUserId` and differing `fromAccount`/`toAccount`.
  - **Log Transfer** (`openTxnModal`/`saveTxn`) now includes a From-Account selector whenever the sender is a non-Aryan user: forced to `'A'` (and disabled) when the recipient is Aryan (a "Transfer to Aryan" can only ever come from Account A); otherwise defaults to `'A'` but is user-selectable. The recipient's credited account is derived automatically, never chosen: `'A'` if the sender is Aryan, `'B'` otherwise.
  - **Withdraw to Cash** (`openWithdrawModal`/`saveWithdraw`) includes an Account selector for non-Aryan users so a withdrawal can be taken from either wallet; legacy withdrawals recorded before this model (no `account` field) default to Account A.
- **Profit-sharing modes** for a friend's application (funding source itself is no longer tracked as a separate concept — every application is applied through the user's own two accounts; these modes decide the split of *both* the deduction and the eventual profit):
  - `'commission'` — the full applied cost is deducted from Account A only (all profit is Aryan's; the user earns a commission % of positive profit as their cut, credited to Account B at settlement). `fundedByMe` is forced to the full applied cost.
  - `'shared'` — both invest their own real stake (two explicit input boxes: Aryan's Invested Amount, User's Invested Amount, kept in sync to always sum to the applied cost) — Aryan's share is deducted from Account A, the user's share from Account B, and each principal is always returned to its own account exactly as invested. Profit splits by investment ratio, credited back to each account at settlement. An optional `bonusToUser` lets Aryan voluntarily shift a flat extra amount of his own share to the user, on top of the ratio split.
  - `'assisted'` — mechanically identical to Shared for the principal (both invest their own real stake, two synced input boxes, each principal returns to its own account regardless of outcome) — but the **profit** is split by a flat `commissionPercent` of profit to the user instead of the invested ratio (rest is Aryan's). E.g. Aryan funds ₹14,000 and the user funds ₹550 of a ₹14,550 application; each gets their own ₹ back untouched, but the *profit* is split e.g. 80% Aryan / 20% user regardless of the 14000:550 stake ratio. This is the mode for "we both put in real money, but we agreed on a commission %, not a ratio." No `bonusToUser` in this mode. (Redesigned in v5.4.15 — see Recent feature history; before that it meant something structurally different.)
  - Applying as Aryan himself (`isMe`) skips profit-sharing and the two-account model entirely — the whole amount and all profit/loss is his, drawn from and realized directly in his own liquid `myAccountBalance()`.
- **Settlement → Transfer to Aryan flow** (structural change): when a friend's application is sold, the full recovered amount (principal + profit, both Aryan's and the user's shares) is treated as landing back in the **user's own two accounts** first — Aryan's share into Account A, the user's share into Account B — exactly like a real IPO refund/payout would. It shows up as part of `owedToMe` / `accountABalance()`, but is **not** added to `myAccountBalance()`. Only when Aryan explicitly transfers it out — via the "Transfer to Aryan" button (transfers the full Account A balance) or "Transfer to Aryan + Extra Amount" (same, plus a manually entered top-up) on the User Detail page — does a real transaction get logged (always debited from Account A), and only then does it appear in Aryan's own account balance. This mirrors the "not allotted → refund lands in user's account" behavior that already existed for rejected applications.
- **Blocked capital while holding**: once an application is allotted but not yet listed/sold, Aryan's invested capital in it is blocked (via `myDeployedCapital()`) and excluded from `myAccountBalance()`. If Aryan funds a *new* application for the same or another user while that capital is still tied up, the new application draws from separate/fresh money — the blocked amount does not silently become available again until it's actually recovered.
- **Money Transfers vs Withdrawals vs Application Funding vs Move Between Accounts** — four distinct concepts, easy to confuse:
  - *Application funding* (`fundedByMe` on an application) is tracked automatically as a live draw on the user's Account A (and Account B in Shared mode) from the moment you fund it — no manual entry needed. `amountGiven` is a separate field for the full cash actually handed over when it's more than Aryan's invested amount (e.g. gave ₹15,000, only ₹14,000 was his stake) — the difference stays permanently owed out of Account A regardless of the IPO's outcome.
  - *Money Transfer* (`state.transactions`) is the only thing that actually moves money between two tracked users' real balances — used both for cash movement unrelated to a specific IPO (advances, repayments) AND as the mechanism that realizes a settled application's profit into Aryan's own account ("Transfer to Aryan" buttons pre-fill and log one of these, always from Account A).
  - *Withdrawal* is money a user takes out of the tracked system entirely as physical cash — it only reduces their own balance (one specific account, for non-Aryan users), doesn't move money to anyone else.
  - *Move Between Accounts* is an internal transfer that moves a single non-Aryan user's own tracked money between their Account A and Account B — doesn't change their total balance, only which account it sits in.

## Known conventions to keep in mind

- Money values are stored as plain numbers (rupees, not paise).
- Dates are ISO strings (`YYYY-MM-DD`).
- IDs are generated with `uid()`, a simple random-string helper — not UUIDs.
- The service worker auto-versions its cache; bump the cache name in `sw.js` if you need to force clients to pick up a new `index.html` immediately (otherwise it updates on next reload after the new service worker activates).
- **A friend's application "profit"/principal is not the same as Aryan's account balance.** Settled amounts sit in the user's two tracked accounts (Aryan's share in `accountABalance()`, the user's share in `accountBBalance()`) until an actual transfer (`state.transactions` entry) moves them into `myAccountBalance()`. Never make a balance-related change that credits Aryan's account directly from `computeApp()` output without going through a real transfer — that reintroduces the "profit shows before it's actually collected" bug this was fixed to avoid.
- **Backup/restore compatibility**: `profitMode`, `bonusToUser`, and `userInvested` are additive fields on `applications`; `fromAccount`/`toAccount` on `transactions`, `account` on `withdrawals`, and non-Aryan entries in `deposits` are additive too — old backups without them still load fine (`profitModeOf()` falls back to the legacy `fundingSource` field; `bonusToUser` defaults to no bonus; missing `fromAccount`/`toAccount` are only relevant to display and don't break balance math since `transfersNetAccount` simply won't match untagged legacy transactions against either account; missing `account` on a withdrawal defaults to `'A'`). No existing field was removed or renamed, so old backups remain fully restorable — though balances computed from a very old backup will reflect the new two-account rules going forward, not a re-derivation of history. Note: `userInvested` on Assisted-mode applications changed *meaning* in v5.4.15 (see Recent feature history) — old Assisted records predating that change should be re-checked, since the field is present in both cases but represents a different thing.
- **Two new localStorage keys live outside `state` entirely** (not part of `lotledger-app-state`, not included in Export/Import Backup): `lotledger-last-backup-at` (ISO timestamp of the last manual export, drives the dashboard backup reminder) and `lotledger-autobackups` (array of up to 3 `{ts, reason, data}` automatic full-state snapshots, taken before imports and at most once/day, used only for in-app "Restore" — separate concept from a manual Export Backup `.json` file).
